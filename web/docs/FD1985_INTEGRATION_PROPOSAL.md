状态：2026-10-10，**已批准分阶段推进；A / B 已完成，C 的最小只读软件基础可运行，真实硬件验收与 D–F 尚未完成**。已建立隔离 Rust 工具链与锁定依赖，没有运行 FD.exe、访问实际串口、读写舵机或烧录。B 的样例 / 草稿与 C 的后端 fake 夹具分别标记，均不代表实际参数或标定。

George 已确认：15 颗舵机均为 **HD-1910-C001**；FE-URT2-C001 当前接 Windows，团队优先需要 Windows / macOS，Linux 也作为目标平台。固件版本、实际 ID、已有装机零位、方向与限位数据尚未提供。下列功能是目标覆盖范围，不能算作当前调试台已有能力。

## 1. 接入方式与真实差距

目标是在 Hatchery Web 中提供 FD1985 的调试、参数、诊断与维护功能，并增加 15 关节批量工作流。FD.exe 是 Windows 原生程序；Web 功能通过共享协议和权威后端实现，原 EXE 作为核对功能行为的参考。[厂商 FD 软件仓库](https://gitee.com/ftservo/fddebug/blob/master/README.md)提供该版本的发布说明。

当前联调、工作台、反馈表、曲线和 3D 仍消费浏览器样例；维护页独立消费最小 Rust 后端只读快照。`src/` 已有 robotd / mediad / duck-control 与协议库的只读 binary / library，完整官方运行源码未迁入。Python 样例仍不承担串口或控制，完整 FD 能力仍需型号协议与逐项硬件验收。

本方案延续 [架构 v2](../../docs/microduck-hatchery-architecture-v2.md) 的 crate 边界、[当前架构](../../docs/ARCHITECTURE.md) 的权威关系和 [冻结 FT 源码审核](PROTOCOL_SOURCE_AUDIT.md)。桌面台架按本次批准的方案分阶段实现，不替换 Radxa 上的整机运行架构。

## 4. 原始值与角度

必须保留三层数据：总线原码 / 寄存器字节、按型号解析的 counts、带校准版本的关节角。UI 默认并列显示位置 `counts` 和角度 `°`；技术详情可查看十六进制原码与解码依据。目标草稿、服务目标回读和实测位置各自保留，误差只在相同单位、相同校准下计算。

根据本地 HD 规格书，默认单圈 12-bit 编码对应 4096 counts/rev：

```text
k = 360 / 4096 = 0.087890625 °/count
encoder_reference_deg = decoded_counts × k
center_reference_deg  = (decoded_counts − 2048) × k

joint_deg = reference_deg
          + direction × (unwrapped_counts − zero_counts) × effective_k

target_counts = zero_counts
              + (target_joint_deg − reference_deg) / (direction × effective_k)
```

前两个参考角仅适用于已确认的单圈默认分辨率。`4095` 对应 `359.912109375°`，不能改成除以 4095。`2048` 是编码器中位；没有装机标定时只显示“编码器参考角”，实际关节角为未知。

`direction` 为机械标定的 ±1。后端统一完成逆转换、整数取整和限位验证，并返回实际量化后的目标；超限拒绝，不能前端静默裁剪。标定角、计数、有效分辨率或模式变化时，草稿必须重新验证，旧草稿不能自动执行。

规格书说明最高分辨率下的多圈位置范围为 ±7 圈，但掉电不保存圈数。多圈 / 单圈 / 改分辨率模式分别建明确转换规则；未知圈数不补零，不盲目取最短路径或 wrap。`unwrapped_counts` 与标定时的 `zero_counts` 必须使用同一计数参考。掉电、设备偏移变更、舵机替换及模式变化按后端规则使旧标定或多圈参考失效。不能把无机械极限的电机理解为装配关节可无限转动。

| 数据 | 当前已知依据 | 显示 / 使用方式 |
|---|---|---|
| 位置 / 目标 | 规格给出默认分辨率；原码符号与多圈解析还需匹配固件 | 保留原码与 counts，符合条件才显示对应参考角 / 标定角 |
| 速度 / 加速度 | 本地规格没有完整寄存器换算 | 先保留 raw 值；核实后增加 °/s 等，不能使用其他型号系数 |
| raw load / 扭矩参数 | FD 中名称与配置表存在歧义 | 保留原始单位；没有扭矩标定不显示 N·m |
| 电流 | 冻结 FT 代码用 sign15 × 6.5 mA，尚未证实适用当前固件 | 保留原码；型号寄存器依据和实测对照确认后才标 mA |
| 电压 / 温度 | 冻结代码为 byte / 10 V、byte °C | 回读与型号协议确认后换算；保留 raw 与有效性 |

本地规格列出模式 0 角度伺服 / 目标电流限力、1 恒速、2 恒流、3 PWM 开环、4 纯位置 PD。规格称出厂模式为 4，[厂商型号页面](https://ftservo.github.io/ftservo-wiki/products/models/hd-1910-c001/main/)另有模式 0 默认的描述，故以实际固件和回读为准。规格还注明过流 / 过压保护默认关闭，过热保护默认开启；保护页面必须读取真实设置，不能显示未经回读的“保护已开启”或直接覆盖阈值。

现有浏览器 0–255 / 中位 128、嘴部 0–127 是演示夹具。它们和 `ui-visual-demo-v1` 3D 映射继续明确隔离；不能乘上 HD 的比例便改称真实数据。以后另设明确标记的 HD 协议夹具，用于检查换算而不冒充测量结果。真实角度接入 3D 还须核对模型轴向与坐标；3D 展示不改变目标或作为校准依据。

## 5. 逐关节标定与批量操作

15 个预期关节始终按左腿 20–24 → 右腿 10–14 → 头颈 / 嘴部 30–34 展示；嘴部 #34 没有 policy_index 仍参与读取、编辑、参数与标定。扫描到的额外 ID 在发现列表单独列出，不能自动绑定到关节。当前显示 / runtime / policy 索引见 [映射夹具](../../protocol/mappings/joints.json)，仍需在正式协议和实机侧核对。

每颗标定保存：设备 / 总线身份、实测 ID、型号 / 固件、模式 / 分辨率、零位 counts、参考角、机械方向、实际上下限、HOME（若已确认）、版本、时间与确认依据。整机标定文件有明确版本和完整性状态；标定 1 颗不能显示 15/15 完成。

推荐流程：

1. 获取唯一总线所有权，读取身份、固件与参数，保存逐颗基线快照；确认发现 ID 与实际安装关节对应。
2. 核对装配参考姿态，读取此时 counts，填写已知角度和方向；用第二个已知姿态核对方向与比例。没有可追溯的零位数据就保持未标定。
3. 根据装配与人工核查确定机械限位；不自动碰撞寻零或通过堵转搜索边界。型号寄存器限位、模型参考限位和实际装机限位分列。
4. 保存 Hatchery 软件标定，后端校验版本、方向、分辨率、范围与数据完整性；再通过有明确授权的低速、小幅单关节运动验收。
5. 单颗验收后才开放已标定范围的联调；对称联动通过各自零位 / 方向转换，不复制 raw counts。左右对称关系必须核对，不能从 ID 推断。

软件标定不改舵机 EEPROM。设备中位校准 / 写偏移是另一项维护操作；会改变编码器参考和持久参数，须单独预览、执行、回读，并使相关旧标定与草稿重新验证。[冻结 feetech.py](https://github.com/fanhao375/microduck-replica/blob/b5381d86b68d2e4f4606170d54d1f3f46d249ffc/tools/servo-web/feetech.py)记录来源作者 HD 固件 3.46 使用 `0x0B` 的经验，不能代替本机固件确认或默认套用另一型号的扭矩寄存器校准写法。

批量范围支持全部、左腿、右腿、头颈 / 嘴部、自定义，并与反馈表 / 曲线显示范围分开。

| 批量操作 | 行为 |
|---|---|
| 参数回读 / 备份 | 后端调度逐颗读取，显示差异矩阵、来源和读取时间，缺失保留原因；同型号不同固件不混表 |
| 草稿应用 | 先展示旧值 / 新值 / 单位 / 存储区域及逐 ID 验证结果；显式执行后显示接受、写入确认、回读一致、到位等不同状态 |
| 批量运动 | 单颗或受控批量按能力发送；普通写 / SYNC_WRITE / REG_WRITE + ACTION 语义分开；同步指令不保证机械同步或原子完成 |
| 批量标定 | 引导逐颗确认姿态、方向与限位；软件配置可一次提交已核实条目，不批量覆盖未知零位 |
| ID / 波特率 / 持久偏移 / 恢复 | 逐颗维护，检查冲突、后续连接变化和读回路径；ID 冲突时要求隔离单颗，不能广播改成同一 ID |
| 扫描 / 步进 | 后端持有有限计划、进度和期限；缺测、故障或资格变化按计划规则中止，前端定时器不发运动循环 |
| 固件 | 协议与恢复验证后逐颗队列；不广播刷全机，不将部分成功显示整机完成 |

反馈不覆盖草稿。载入姿态 / 参数文件只产生草稿和差异，打开页面、切页、拖动、重连或回放都不执行历史目标。没有标定的装配关节禁止角度控制及联调；如需裸机 raw 测试，必须另有明确的台架安装状态、限制与授权。

## 7. Windows / macOS / Linux 部署

两种部署共用 UI、协议与权威控制规则：

```text
桌面台架：Browser → 本机 loopback gateway → shared RPC
                  → src 的权威维护服务 → duck-control / safety → FE-URT2 → HD

整机运行：Browser → Radxa Web / media gateway → shared RPC
                 → robotd → duck-control / safety → 实际 FT 总线
```

**Radxa Zero 3W 是整机主要运行平台。** Windows / macOS 台架维护是辅助入口，因当前接线与团队需要先验证；Linux 桌面与 Radxa 分开验收。已建立 robotd 的最小只读运行入口，不为调舵机启动策略、Camera、ToF、官方 HAT 或整套 daemon。当前没有完整 safety / 策略控制实现，也不宣称完整官方 robotd 已在桌面编译。

工具只负责启动与通过 RPC 访问控制服务，gateway 只传输与提供页面；权威能力仍实现于 `src/`。现有 `tools/hatchery-shell` 保持只读样例，不升级成第二串口控制器。也不同时保留独立 servo-web 轮询进程与 robotd 抢占同一总线。

| 平台 | 必须核对的实际事项 | 当前状态 |
|---|---|---|
| Windows | COM 枚举、真实 USB 芯片与驱动、串口独占、断线 / 重插后的身份；打包与后台服务启动 | binary 构建及 fixture 链路通过，未访问实际串口 |
| macOS | Apple Silicon 优先，Intel 支持范围单列；实际 `/dev/cu.*` 设备、驱动 / 签名、权限、串口占用与休眠恢复 | Apple Silicon 源码检查通过；未链接、运行或 USB 验收，Intel 未验收 |
| Linux 桌面 | USB 枚举、权限组 / udev、稳定设备身份、抢占串口的系统服务 | 目标平台，未测试 |
| Radxa Zero 3W | 镜像、实际 UART / USB 节点、系统权限、FT 固件与 robotd 部署 | Linux ARM64 源码检查通过；未链接、部署或实机验收 |

串口路径由后端发现 / 配置，不硬编码 COM3、`/dev/ttyUSB0` 或官方板卡节点；实际 adapter 的 VID / PID / 序列信息用于识别，不能假定全部 FE-URT2 使用同一芯片。厂商将 [FE-URT2-C001](https://www.feetech.cn/530962)定义为 USB Type-C 转 TTL / RS485 适配器，当前 HD 路径使用 TTL，不因适配器有其他接口就改变舵机协议。

本机 gateway 默认只绑定 loopback，同时从同一 localhost origin 提供静态页面与 HTTP / WS，校验 Host、Origin 与会话凭证；不能开放通配来源或只依赖 CORS。`file://` 单文件原型继续用于离线样例，真实连接从本机同源入口打开。远程整机 gateway 的认证与网络部署另行验收。

正式 IPC 语义一致，传输层按平台配置。Tokio 的 [UnixListener](https://docs.rs/tokio/latest/tokio/net/struct.UnixListener.html) 仅在 Unix 提供；桌面可采用 loopback TCP RPC，保持消息结构与命令模型不变，协议类型库不引入 HTTP / Tokio 运行职责。浏览器直接串口能力不作为必要条件，保持不同浏览器访问同一 Web 的路线。

前端继续原生 JS 与现有 Three.js，无新增 UI、物理 / RL 依赖。最小 Rust 后端锁定 serde 1.0.229、serde_json 1.0.151、serialport 4.10.1 与 tiny_http 0.12.0；[依赖 / FT 来源审核](../../docs/FT_READ_ONLY_SOURCE.md)明确许可与版本。Linux 关闭默认 libudev feature，USB 枚举元数据可能不完整。构建、目标源码检查、页面可用和 USB 实测分别验收。

## 8. 协议、所有权与断线

状态至少携带设备 / 会话身份、型号 / 固件 / profile 版本、实际模式、校准版本、各字段原值和单位、逐关节采样时间、数据年龄、真实 / fake / sim 来源、总线所有者与能力。UTC Unix 时间用于记录；单调时间用于期限和响应统计，两者分开。读取 15 颗的轮询结束时间不能冒充每颗同时采样。

命令至少含 command_id、会话、目标 ID、预期模式 / 校准版本、有限期限和参数。后端分别报告接收、拒绝、已写入、ACK（若存在）、回读一致、运动到位 / 超时及逐项原因。`SYNC_WRITE` 没有逐 ID ACK；回读一致也不等于机械到位。禁止用会重写目标的“验证”接口冒充只读确认。

由唯一控制服务调度读取与写入。通信测试与固件升级属于当前 robotd 所有者的维护序列，先暂停常规轮询，不另开第二总线服务。FD.exe、独立校准服务和另一个 robotd 不能同时访问该串口；进程内 mutex 不足以管理跨进程所有权。后端租约与 OS 串口独占分别验证，打开 / 加锁失败拒绝访问，不能强制接管已打开的 FD；[Windows 串口句柄规则](https://learn.microsoft.com/en-us/windows/win32/devio/communications-resource-handles)要求独占访问，POSIX 独占仍需按所选库与实机环境测试。维护与整机模式切换必须结束旧活动、确认释放并重新读取身份 / 状态；租约过期后旧客户端不能继续执行。

扫描 / 步进等动作试验由后端执行有限计划。页面失联、命令到期、服务退出、USB 拔出或模式变化后停止接收旧目标，具体电机停止 / 卸载策略按实际模式确认；USB 断开后主机未必能再发指令，不能承诺失联一定立刻停机。重连先回读，不能自动使能、重刷固件或续发队列。取消队列、关闭输出、软件停止、释放控制权和物理急停分别定义，release 不是停止。
